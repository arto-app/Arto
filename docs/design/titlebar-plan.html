Arto ／ 実装計画

帯をゼロにする

決まったのは E（タイトルバーに畳む。B のグリフはその中に住みます）と D（⌘K をコマンドパレットに）。 3つのプラットフォームすべてで行い、macOS はネイティブメニューを残します。窓ボタンも各 OS の作法どおりに揃えます。 着手の前に、沈む可能性のあった6点を先に調べました ―― 5つは通り、1つは通りませんでした。

先に潰した6点

すべて tao 0.34.8 / wry 0.53.5 / dioxus-desktop 0.7.10 ―― いまロックされている版のソースで確認しています。

①
HTML から窓をドラッグできるか

タイトルバーが HTML になるので、押して動かしたら窓が付いてこなければなりません。 -webkit-app-region: drag は Chromium だけのもので、WKWebView にはありません。 ―― ですが不要でした。tao の macOS 実装は performWindowDragWithEvent: を呼んでおり、 dioxus は desktop.drag() として公開しています。3つとも同じ1行で済みます。 通る

②
装飾を外した窓をリサイズできるか

macOS はそもそも装飾を外しません（③ の表）。枠は native のままなので OS 任せ。 Windows は tao 側が WM_NCCALCSIZE / WM_NCHITTEST を処理していて、 コメントにも「装飾なし窓のリサイズを許可する」と書かれています。Linux は drag_resize_window(direction) が実装済み。 通る

③
窓ボタンに必要な API があるか

set_minimized / set_maximized / is_maximized / set_fullscreen / fullscreen / is_decorated、すべて tao::window::Window にあります。 dioxus::desktop は pub use tao しているので、プラットフォーム拡張トレイトもそのまま使えます。 通る

④
Windows 11 のスナップレイアウト

最大化ボタンにホバーすると出るあの吹き出しは、WM_NCHITTEST に HTMAXBUTTON を返して初めて出ます。 tao が返すのは HTCAPTION と HTCLIENT だけ。 逃げ道の with_msg_hook はイベントループのキューの手前に入るもので、 WM_NCHITTEST は SendMessage で窓プロシージャへ直接届くためキューを通りません ―― 見ることも答えることもできません。 通らない

⑤
GNOME の窓ボタン配置を読めるか

org.gnome.desktop.wm.preferences の button-layout は左右も順序も利用者の設定です。 gio 0.18 は依存の木に既にあり、読めます。ただし Settings::new はスキーマが無い環境で abort します（GNOME でない Linux は珍しくありません）。 SettingsSchemaSource::default()?.lookup(id, true)? で存在を確かめてから作る必要があります。 通る（作法つき）

⑥
位置とサイズの保存が壊れないか

capture_window_metrics は outer から chrome_inset（タイトルバーの高さ）を引いて inner を出しています。 装飾を外すと inset は 0 になり、式はそのまま成立します。 ただし装飾ありで保存された state.json からは、タイトルバー1本分だけ大きく復元されます ―― 移行時に一度だけ効く歪みです。 通るが、移行に一手

実装イメージ

3つとも「ヘッダーがそのままタイトルバーになる」形です。帯は1本も無く、本文は窓の縁まで届きます。 違うのは窓ボタンを誰が描くかだけです。

macOS ―― 信号機は AppKit のまま

装飾は外しません。タイトルバーを透過にして本文をその下まで伸ばすだけなので、 ドラッグ・リサイズ・信号機・緑ボタンのフルスクリーンは全部 native の挙動です。 画面上端のメニューバーにも一切触れません。左に信号機の分だけ場所を空けます。

段取り

D

1　コマンドパレット

  • Action に palette 用の名前を足します。動作（cursor.down など）は キーであってコマンドではないので、名前を持たせません ―― Option がその判断を型で表します。
  • 空クエリのときは履歴だけ。⌘K → ⏎ が「直前に戻る」であることは変えません。
  • 打ち始めたらコマンドを上、文書を下。絞り込みは既存の visits::matches と同じ規則で。
impl Action {
    /// パレットでの名前。動作には無い ―― cursor.down はキーであって
    /// コマンドではないので、一覧に出す意味がありません。
    pub fn command_label(&self) -> Option<&'static str> {
        Some(match self {
            Self::FileOpen => "Open File…",
            Self::WindowDuplicate => "Duplicate Window",
            Self::ContentsToggle => "Contents",
            Self::CursorDown | Self::ScrollDown | Self::ContentNext => return None,
            …
        })
    }
}
E-1

2　macOS のタイトルバー

  • いちばんリスクが低く、いちばん早く形が見えるのでここから。
  • ネイティブメニューは menu.rs のまま。触りません。
  • 信号機の位置をヘッダーの 30px の当たりに合わせ、CSS 側で左に空きを作ります。
  • フルスクリーン中は AppKit が信号機を隠すので、空きも畳みます（Resized で見直し）。
#[cfg(target_os = "macos")]
{
    use dioxus::desktop::tao::platform::macos::WindowBuilderExtMacOS;
    // 枠は残す。タイトルバーの描画だけを譲ってもらう形なので、
    // ドラッグもリサイズも信号機も AppKit のまま動きます。
    builder = builder
        .with_titlebar_transparent(true)
        .with_fullsize_content_view(true)
        .with_title_hidden(true)
        .with_traffic_light_inset(LogicalPosition::new(18.0, 16.0));
}
E-2

3　Windows と Linux

  • 装飾を外し、窓ボタンを自前で描きます。二度手間を避けるため、2つは同じコンポーネントで、並びだけ差し替えます。
  • タイトルバーの空き地を押したら drag()、ダブルクリックで最大化・元に戻す。
  • Linux は8方向のリサイズ帯を自分で持ちます（Windows は tao の枠が担当）。
  • Linux の並びは button-layout。読めなければ右固定。
#[cfg(target_os = "windows")]
{
    use dioxus::desktop::tao::platform::windows::WindowBuilderExtWindows;
    // 影を残すと、tao がまだ持っている枠でリサイズの当たりも生きます。
    builder = builder.with_decorations(false).with_undecorated_shadow(true);
}

#[cfg(target_os = "linux")]
{
    builder = builder.with_decorations(false);
}
// GNOME のスキーマが無い機械で Settings::new は abort します。
// 先に在ることを確かめてから作ります。
#[cfg(target_os = "linux")]
fn button_layout() -> Option<String> {
    let source = gio::SettingsSchemaSource::default()?;
    source.lookup("org.gnome.desktop.wm.preferences", true)?;
    let settings = gio::Settings::new("org.gnome.desktop.wm.preferences");
    Some(settings.string("button-layout").to_string())
}
E-3

4　掃除

  • menu.rs（muda）を macOS 専用に。Linux で窓の中にバーを描かせません。
  • win_hamburger.rs を app_menu.rs に改名し、3つとも同じものを使います。
  • ヘッダーはタイトルバーの中身になるので、header.rs と titlebar.rs の境目を決めます。
  • chrome_inset の意味が変わるので、⑥ の移行を1度だけ通します。

残る危なさ

  • ④Windows のスナップレイアウトは出ません。調べた結果、tao の口からは届きません。Win＋矢印と、端へのドラッグは普通に効きます（窓は普通のトップレベルのままなので）。どうしても要るなら HWND を自前でサブクラス化する話になり、windows クレートへの直接依存と unsafe が増えます ―― 別の判断として切り出します。
  • 高WebView がマウスを飲む。ドラッグは押した瞬間に drag() を呼ぶ必要があり、テキスト選択やボタンの上では呼んではいけません。当たり判定の線引きを間違えると「窓が動かない」か「文字が選べない」のどちらかになります。
  • 中ダブルクリックで最大化。OS がやってくれていた作法で、自前になります。3つとも同じ判定にします。
  • 中HiDPI と分数スケール。窓ボタンは物理ピクセルに寄る部品なので、150% や 175% で滲みやすいところです。Linux の実機で見ます。
  • 低復元位置のずれ。⑥。装飾ありで保存された値から一度だけ、タイトルバー1本分。
