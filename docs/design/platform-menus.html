メニューの居場所

macOS では、メニューは画面上端の OS のバーに載ります ―― 作法どおりで、窓の中を 1px も使いません。 Linux と Windows にその場所はありません。いま Linux では、静かにしたヘッダーの真上にもう一段、灰色の帯が乗っています。 クロームを削って買った静けさを、そのまま返してしまっている状態です。

いま起きていること

下は実機のスクリーンショットです。上から、OS のメニューバー（7語）、Arto のヘッダー、本文。 帯が2本あります。片方は私たちが 16px のグリフと 30% の濃度まで削ったもので、 もう片方は GTK が描いた、テーマにも従わない灰色です。

ヘッダーのハンバーガー

ネイティブメニューが無いので、既に自前のメニューを1グリフに畳んでいます（win_hamburger.rs）。答えは既にある

つまり答えは既にコードの中にあります。Windows のためだけに書いたものが、Linux にも要るものでした。 以下は、それを含めた5つの置き場所です。

何で判断するか

メニューを消す案は採りません。「めったに使わないものは ⌘K とメニューだけ」は既に決めた配置規則で、 メニューはその受け皿です。決めるのは居場所だけです。判断はこの4つで行います。

  • 1帯を増やさない。ヘッダーは1本。2本目は、静かなクロームが買ったものを打ち消します。
  • 2テーマに従う。窓の中にあるものが GTK の灰色のままだと、ダークにしたときそこだけ浮きます。
  • 33つで同じ規則。同じ操作が同じ場所にある。プラットフォームごとに説明の要る UI は覚えられません。
  • 4入口は見えている。キーボードだけの機能は、知っている人にしか無いのと同じです。

並べて見る

案帯を増やさないテーマに従う3つで同じ規則入口が見える費用
A　OS メニューバー✗✗✗✓なし
B　ヘッダー左端に1つ✓✓✓✓小
C　レールの足元✓✓✓狭い窓で✗小
D　⌘K に集約✓✓✓✗中
E　自前タイトルバー✓✓✓macOS は別✓大

A だけが4つのうち3つを落とし、しかも唯一「もう書いてある」案です。 B はすでにリポジトリの中にあるものを 1 プラットフォーム広げるだけで、4つとも満たします。

段取り

いま　B

  • win_hamburger.rs の cfg(target_os = "windows") を外し、macOS 以外で出す。
  • menu.rs（muda）は macOS 専用に絞る ―― 窓の中にバーを描かせない。
  • グリフはヘッダーの左端、他と同じ静かな操作子（16px・stroke-width 1.5・30px の当たり）。
  • 中身は既存のメニューと同じ並びを、既存の context_menu で描く。

次　D

  • パレットにコマンドを流す。Action は既に名前と説明を持っているので、一覧はそこから作れます。
  • B のグリフは入口として残す ―― 見える入口と、打って届く道の両方。

いつか　E

  • ヘッダーごとタイトルバーに畳む。本文がいちばん広くなるのはこれだけです。
  • 窓の作法を全部引き受ける覚悟ができてから。

macOS は触りません。あそこのメニューバーは窓の外にあり、費用を払っていません。 3つで同じ規則、というのは「同じ操作が同じ場所にある」ことであって、OS の作法を捨てることではありません。
