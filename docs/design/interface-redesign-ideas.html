3つの設計原則

原則 01 常設は1枚まで

同時に置いておいて良いパネルは1枚。2枚目からは「呼んだときだけ出る」ものに落とす。

原則 02 一覧は縦に伸ばす

横並び固定幅は本数に耐えない。開いている文書も履歴もお気に入りも、スクロールする縦のリストへ。

原則 03 寿命を意図に合わせる

文書は長生き、探索は一瞬、設定は別ウィンドウ。ホバーで開くものは、意図の表明になっていない。

案 ARail — 常設を左1枚に畳む

左の1枚に「ファイル / 開いている / 履歴 / お気に入り」を集約し、タブバーと右サイドバーを廃止します。 現状の延長線上にあり、移行コストが最も低い案です。

Arto

Arto — the Art of Reading Markdown. A desktop app that renders Markdown the way GitHub does, locally and offline.

Why

Most Markdown tools are built for writing. Arto is built for reading: the name is short for “Art of Reading”.

Features

GitHub-accurate rendering with the extended syntax, auto-reload when the file changes on disk, and no network required.

$ arto page README.md
Contents

左レールでパネルの中身を切り替えます。ルートは複数持て、開いている文書は縦リストなので12本でも100本でも壊れません。 本文右端の細いガターが目次です ―― 見出しの深さが目盛りの長さ、青が現在地、黄がピン留め検索のヒット位置。画面端ではなく本文の一部なので、通りすがりに開くことがありません。

変わること

  • −タブバーを廃止。「開いている」は左パネルの縦リストに。ウィンドウタイトルが現在の文書名になりますタブのドラッグでウィンドウ間移動していた操作は、リストのドラッグに移ります
  • −右サイドバーを廃止。目次は本文右のガター、検索は ⌘F のバーに統合ピン留め検索の色はガターの目盛りに載るので、チップ列も不要になります
  • +ワークスペース＝複数ルート。フォルダを追加していける「基点をひとつだけ」という制約が消えます
  • +履歴セクションで、閉じた文書まで遡れる
  • →ヘッダーは「戻る/進む＋パンくず」だけ。コピー・再読込・全幅・テーマは右クリックとメニューバーへ

評価

向いている場面 ―― 複数のリポジトリのドキュメントを行き来する、常に手元に一覧が欲しい使い方。 既存の状態モデル（サイドバー、タブ、履歴）をほぼそのまま並べ替えるだけなので、実装リスクが一番低い案です。

弱いところ ―― 「常設1枚」はまだ画面を取ります。読むことだけに集中したい瞬間には、結局たたむことになる。 そこは ⌘B の一発でゼロにできる、という逃げ道でカバーします。

B

案 BFocus — 常設ゼロ、呼べば出る

画面には本文しか置きません。移動はすべて ⌘K のひとつの入口に集約し、 「開いている / 最近 / お気に入り / ルート配下」を同じリストの絞り込みとして扱います。

Markdown is where documentation, communication and thinking now live, and reading it deserves more than a preview pane.

Features

GitHub-accurate rendering with the extended syntax, auto-reload when the file changes on disk, and no network required.

⌘K ひとつで、開いている文書・最近読んだもの・お気に入り・ルート配下のファイル・コマンドを横断します。 タブも履歴一覧もお気に入りパネルも、この1枚の別の見え方として吸収される、というのがこの案の主張です。閉じれば画面には本文しか残りません。

変わること

  • −タブ・両サイドバーの常設・ピン留めチップ・ヘッダーのボタン群をすべて廃止読んでいる間、画面上の恒久的な要素はゼロになります
  • −画面端のホバートリガーを廃止。開くのは常にキーかメニューから誤爆が構造的に起こり得なくなります
  • +⌘K 移動 / ⌘J 目次 / ⌘F 検索 / ⌘B ファイラー ―― すべて一時的なオーバーレイ、esc で消える
  • +スクロール中はタイトルも隠れ、上端に戻すと出る
  • →すべての操作は右クリックメニューからも到達できるようにするキーボードを覚えないと何もできない、という状態は避けます

評価

向いている場面 ―― 読むことが主目的で、キーボードに手が乗っている使い方。 「読むのに集中しづらい」という不満に対しては、3案で最も直接的な答えになります。

弱いところ ―― 発見性。何ができるアプリなのかが画面から読み取れません。 初回起動時のヒント、右クリックメニューの充実、? のショートカット一覧（既にある機能）で補う必要があります。 「今どのファイルを開いていたか」を思い出せない不安も残るので、⌘K の初期表示は「開いている」順にします。

C

案 CLibrary — タブを捨て、書斎を持つ

「開いている文書の集合」という概念自体をやめる案です。ウィンドウは常に1本の文書を読んでいる場所で、 移動の記録は軌跡（trail）が持ちます。お気に入りと履歴は、起動時に開くライブラリという一等地に昇格します。

Contents

読書中の画面。上の軌跡が「どこから来たか」を保持し、戻るはここを遡ります。 2本並べたいときだけ ⌘\ で分割し、複数ウィンドウは今のまま使えます。

変わること

  • −タブという概念そのものを廃止「12本開いている」という状態が発生しません。管理する対象が消えます
  • +ライブラリが起動画面。お気に入り・最近・ルートが一等地に出ます

  • →ファイラーは ⌘B の一時オーバーレイ、またはライブラリ内のツリー

評価

向いている場面 ―― 数本の文書をじっくり読む、拠点としての使い方。 「お気に入りが小さい」「履歴が見えない」への答えとしては最も強く、Arto の "Art of Reading" という立て付けにも最も忠実です。

弱いところ ―― 10本を高速に行き来する作業には向きません。タブを実際に使いこなしている場面があるなら、この案はその体験を失わせます。 3案で最も大胆で、実装も状態モデルの作り直しになるため、一番重い案です。

機能の取捨

落とす候補と、その受け皿

「落とす」は機能を消すことではなく、受け皿を決めて場所を移すことです。 受け皿のない削除だけは避けます。

落とす / 移す

  • −タブバー（横並び固定幅）3案とも廃止。受け皿は縦リスト、⌘K、または軌跡
  • −右サイドバーの常設と、画面端のホバートリガー目次は本文右のガターへ。開くのはキーとメニューだけに
  • −ピン留め検索チップの列色は目次ガターの目盛りに載せる。位置と色が同時に分かるので、情報量はむしろ増えます
  • →ヘッダーのコピー・再読込・全幅・テーマ右クリックメニューとメニューバーへ。テーマは設定にもあり、日に何度も切り替えるものではありません
  • →設定タブ独立ウィンドウへ。macOS の作法どおり ⌘, で開き、閉じれば消えます
  • →サイドバーの「全ファイル表示」トグル設定項目へ。日常的に切り替えるボタンではありません
  • −サイドバー内の戻る/進む（ディレクトリ履歴）パンくずのクリックで代替できます

残す / 強くする

  • +複数ルート（新規）今の単一 root_directory を Vec に。3案すべての土台になります
  • +横断的な履歴（新規）タブごとの戻る/進むとは別に、アプリ全体の閲覧履歴を持ちます
  • +お気に入り案 C ではライブラリの主役、案 A では専用セクション。いずれにせよ従属をやめます
  • +子ウィンドウ（Mermaid・画像・数式）「見たいときだけ出て、閉じれば消える」という、既に正しく設計されている部分です
  • +テーマ・ズーム・キーバインド・自動リロード読むための設定。触るのは常設ボタンからではなく設定から
  • +複数ウィンドウとドラッグ&ドロップ「並べたい」を明示する手段として、むしろ重要度が上がります

進め方

案を選ぶ前に、効く手当てがあります

Phase 0 は3案すべてに共通の下ごしらえで、どれを選んでも無駄になりません。 不満のうち3つはここで消えます。

Phase 0 — 共通

受け皿の要らない手当て

  • 設定をタブから独立ウィンドウへ（TabContent::Preferences の廃止）
  • 画面端のホバートリガーを廃止し、⌘B / ⌘⌥B とメニューに一本化
  • ヘッダーの常設ボタンを右クリックメニューとメニューバーへ移す
Phase 1 — 土台

状態モデルを先に整える

  • ルートを複数持てるようにする（root_directory → ルートのリスト）
  • アプリ横断の閲覧履歴を持つ（タブごとの履歴とは別レイヤー）
  • 「開いている / 最近 / お気に入り / ルート配下」を、ひとつの検索可能なリストとして扱える内部 API にする
Phase 2 — 分岐

案を選んで表層を差し替える

  • 案 A なら左レール＋パネル、案 B なら ⌘K パレット、案 C ならライブラリ画面
  • Phase 1 の API があれば、どの案も同じデータの別の見せ方として実装できます
  • 目次ガター（本文右の目盛り）は案 A / C 共通の部品
Phase 3 — 掃除

受け皿ができたものから落とす

  • タブバー、右サイドバー、ピン留めチップのコンポーネントと CSS を削除
  • 関連するキーバインドとメニュー項目の整理（tab.* の扱いを決める）
  • 設定画面から、なくなった項目を削る

推奨

案 A を土台にして、案 B の ⌘K を全案に載せるのが、失うものと得るもののバランスが最も良いと考えます。 案 A は既存の状態モデルの並べ替えで済み、⌘K は他の何を選んでも単独で価値があるからです。 案 C のライブラリは、その後「新規タブの代わりに開く画面」として足せます ―― 3案は排他ではありません。

逆に、いま最も切実な「読むのに集中できない」を最短で解くなら、案 B の思想で Phase 0 を強めに振り切る手もあります。 そこは次の設問の答え次第です。

決めてほしいこと

ここが決まると、案が一本に絞れます

01

タブは残しますか、捨てますか

最大の分岐です。「12本開いている状態」に価値があるなら A、状態そのものを消したいなら C。判断材料は「実際にタブを切り替えて往復しているか、単に閉じ忘れているだけか」です。

02

キーボード中心で良いですか

案 B は ⌘K を覚えることが前提です。マウスだけでも完結させたいなら、常設パネル（案 A）かライブラリ（案 C）が要ります。

03

複数ルートは保存したいですか

「ワークスペース」として名前を付けて保存・切り替えたいのか、その場で足すだけで良いのか。前者なら設定と config.json に構造が増えます。

04

目次は常に見えているべきですか

本文右の目盛りガター（常時・情報量少）か、⌘J のオーバーレイ（一時・情報量多）か。長い技術文書を読む頻度で決まります。
